What groups over MCP buy you, measured on one giant tools + skills catalog

An MCP server with a lot of tools and/or skills has a problem: by default, every tool's schema goes into the model's context on every turn, whether the task needs it or not. The MCP Progressive Disclosure working group (its repository, its Discord channel) has a draft Groups extension that answers this with two methods. groups/list returns a short list of named bundles, and groups/get returns one bundle's tools, prompts, resources and instructions when the agent decides it needs them. A companion document asks how Groups should sit next to Skills over MCP, which discloses instructions the same way.

I built both on a real catalog to see what the numbers look like. The server I used for this experiment is Cloudflare's own API MCP server, which includes 3,036 generated tools from 136 products, along with five of Cloudflare's published skills. One Worker serves it four ways: flat, and under each of the three positioning options the working group is weighing. Everything below was measured on the 2026-11-07 drafts of both documents.

Three things the numbers say

1. Groups solve a context-size problem, and it is definitely a problem at this scale. The flat tool list for 3,036 tools is 1.38 million tokens, more than any model can read. The groups list for the same catalog, using 139 top-level groups, is 5.5 thousand tokens. The bundle the agent then fetches for a task is the same size whether the catalog has 238 tools or 3,036. On a 238-tool subset the saving is still 157 thousand tokens down to about 700.

2. Groups did not change what tool or skill the model picked. I gave sixteen models twenty tasks that describe a job without naming the product ("Serve 50 GB of user uploads to browsers on another origin, so cross-origin headers are needed") and asked where they would look first. Every hosted model landed within two tasks of itself whether it saw 13 groups, 139 groups, 238 flat tool names or 3,036 of them. The draft already says this in its own evidence section: groups keep unread schemas out of context, but they do not beat using a flat list when it came to selection.

One tweak that did change the selection result between lines was adding the five-line skills index to the prompt, which lifted the 'flat list' variant scores by up to 17 of 20 for some models.

3. When testing through a real harness, the host's own tool search gets the same result. I wrote a Claude Code mod that implements the groups extension and ran the twenty tasks as 180 headless sessions, three models, three ways. Sonnet and Opus finished every task in every variant. Haiku finished 16, 18 and 19.

Groups cost one extra turn, because opening a bundle is a round trip. Nested bundles sometimes cost two. The prompt cache held when opening bundles. Registering a group's tools added about 2.7 thousand tokens on a 42 thousand-token cached prefix, which is the behavior the draft's caching section predicts. Claude Code's own tool search, with nothing from the extension, reached the same completion and the same token band using one less turn.

So what do groups solve?

Against the working group's own four criteria: groups deliver initial context size and total tokens, leave task completion unchanged for frontier models, and add a turn in exchange for each harness not needing to invent its own solution for reducing token bloat. On this catalog a host with tool search gets the token result without a protocol change. What groups add that tool search cannot is the bundle: a server-authored set of tools with the instructions and the skill that go with them, delivered together, scoped to the caller, and a path for clients that have no tool search of their own. It also provides the same solution for skills served over MCP, and any other MCP primitive besides just tools. Harnesses are still working out how to handle large numbers of file-based skills (how harnesses bound their agent skills catalog), so a server-side bundle is one more reason to serve skills over MCP.

Two things the server author controls turned out to matter more than the mechanism itself. Group descriptions directly influenced the whole selection: my templated one-liners ("Call the Cloudflare queues API directly") cost the mid-size open models up to six of twenty tasks at 139 groups, which is what the draft's guidance warns about. And a server that offers both a workflow group and a plain toolset group for one product splits the models between them, so it should say in the descriptions which to open when.

Caveats

This experiment only included one sample per task. The group names and descriptions are mine, not Cloudflare's. The full completion run using Claude Code used one model family on one host. It also tested against a dry-run server that returns the request a tool would send and never any data. The 'flat list' baseline is a mode Cloudflare itself ships only as an escape hatch; the server's default is Code Mode, which I did not compare. The write-up has every table, every accepted answer and every limit, and the 180 sessions are also there to review.
