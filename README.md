# MCP progressive disclosure evals

Measurements of the MCP working group's draft [Groups extension](https://github.com/modelcontextprotocol/progressive-disclosure-wg/pull/19) on a large real catalog: Cloudflare's API MCP server (3,036 tools) with five of Cloudflare's published skills. One Cloudflare Worker serves the catalog flat and under each option in the [positioning document](https://github.com/modelcontextprotocol/progressive-disclosure-wg/pull/22) for Groups against Skills over MCP.

## Findings

- **Tokens.** The flat `tools/list` for 3,036 tools is 1.38M tokens, more than any model can read. With 139 generated groups a client reads 5.5k tokens before it picks. As names and first description lines, the group listing is 3.9k tokens for those 139 groups and 16.5k for 271 groups with rewritten descriptions. What the model reads after it picks a group is the same at either catalog size: the group's tool schemas and the skill body.
- **Selection, hosted models.** Groups did not measurably change what the ten hosted models picked. Each scored 16 to 20 of 20 in every groups arm on both task sets. With the skill index in the prompt they scored 17 to 20 on flat tool names, counting a lookup such as `zones_list` as a first call on the held-out set. These task sets cannot detect a small difference.
- **Selection, open models.** Templated group descriptions cost the open models. On the full catalog they scored 10 to 19 of 20 on 139 generated groups and 17 to 20 on 271 groups whose descriptions carry task vocabulary, which is the guidance in #19. On the held-out tasks five of the six lost 3 to 14 tasks to the templated descriptions. The held-out rules forbid the product name, so that gap is partly by construction.
- **Duplicate listing.** Option 2 lists each workflow in both `groups/list` and `skills/list`. On the as-generated server, models answered with the skill alone on up to 4 of 20 tasks that needed the product's tools, a path that on a real client loads the skill's instructions without those tools. The rewritten build removed most of these. With every skill still listed, 8 skill-only answers were left across all models, all on two Durable Objects tasks where the skill is an accepted answer. Leaving grouped skills out of `skills/list` for a groups client removed those and left every model within one task of its score. A host can do the same on its own. Against the as-generated server, a prompt that showed each workflow once drew the group of the same name in 134 of 145 answers, on the tasks that had drawn the skill. Across four models and two catalog sizes, the score stayed level or rose in seven of eight cells.
- **Claude Code.** Sonnet completed 20 of 20 tasks in every condition of both rounds, and Opus missed one. In round two groups read 1.54M to 1.75M input tokens per model, the host's tool search 1.51M to 1.60M, and all schemas up front 15.9M to 17.4M. Groups took a median 5 turns on the product tasks against 3 or 4. The groups arm loaded its scoped tools through the host's tool search, so it shows the two composed. With tool search off, each group open rewrote the cached prefix and the run cost 2.2 to 2.4 times as much.
- **Open models, appending tools.** These runs went through the Hugging Face router, where neither Baseten model loaded tools mid-session in the request shapes tried on 2026-11-12, so an appending client re-sends a longer `tools` array. Each open then re-read what followed the tool block, and the re-read grew with the session. Over six turns appending cost 1.34 to 1.38 times the fixed tool set on the subset and 1.9 to 2.4 times on the full catalog, where every open re-read the 16.5k-token group listing. Putting the listing in the first tool's description brought that to 1.3 to 1.4 times.
- **Open models, 30 turns.** On DeepSeek V4.1 Flash, six sessions per cell, with 2k-token tool results: appending passed all schemas up front between turns 10 and 13 when that session started cold, and by turn 3 when the schemas were already cached. It cost 1.6 and 2.0 times as much by turn 30. With dry-run-sized results appending ended cheaper on average: 0.71 times the cold start, from two sessions, and 0.91 times the cached one, where two of the six session pairs ended slightly above. GLM-5.3 Flash's cache missed with no tool change in long sessions, so its cells measure the endpoint more than the client.
- **Open models, fixed tool set.** It kept the cache across opens on both Baseten endpoints. It completed about as many turns as appending: DeepSeek 90 of 90 against 87, Qwen3.6 84 against 85, Gemma 64 against 49, and GLM 81 against 88, or 85 once the loop accepted a misplaced tool name. Its arguments validated at least as often. On DeepSeek it cost 0.38 to 0.78 times appending. On DeepInfra, where the cache does not change the bill, it sent more input tokens and cost 0.96 times appending for Qwen3.6 and 1.55 times for Gemma.
- **Open models, deferred loading.** Baseten's own endpoint can load tools mid-session: a tool sent with `defer_loading` stays out of the prompt, and a `tool_reference` in a tool result loads it. The 2026-11-12 probe sent a different request shape, which Baseten ignores or rejects. On DeepSeek V4.1 Flash at Baseten direct, a client that loads each group this way re-read a median 33 tokens after an open, against 3.0k for appending. Over six turns it cost 0.76 times appending and 1.04 times the fixed tool set, and completed 87 of 90 turns against 90 and 90. GLM-5.3 Flash loaded tools the same way in one probe conversation, and its sessions were not run. Sent through the Hugging Face router or OpenRouter, the same request did not load the tools.
- **Spec gaps.** Option 2 of the positioning document works as written on the shipped SDK. Neither document says whether a skill a group lists stays in `skills/list`, and the SDK lists every SKILL.md in `resources/list` by default. Option 3's flattening of a SKILL.md folder into instructions drops the skill's entry, digests and the root for its relative links.

## Terms

Documents under test:

- #19: the working group's draft [Groups extension](https://github.com/modelcontextprotocol/progressive-disclosure-wg/pull/19), read at `15b2a5c`. It adds `groups/list` and `groups/get`. A group's tools come back from `groups/get` and stay out of `tools/list`.
- Options 1, 2 and 3: the three ways to combine Groups with Skills over MCP in the [positioning document](https://github.com/modelcontextprotocol/progressive-disclosure-wg/pull/22) (#22), read at `5e9ff2f`.
- Skills extension: [SEP-2640](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2640), which serves skills through `skills/list` and `skills/get`.

Catalog:

- Subset: 237 tools from 10 products of Cloudflare's API MCP server ([cloudflare/mcp](https://github.com/cloudflare/mcp)), with five skills from [cloudflare/skills](https://github.com/cloudflare/skills). Round one counts say 238 because the servers also listed a `demo_info` tool until 2026-11-09.
- Full: all 3,036 tools, from 136 products. It runs locally only.
- Dry run: every tool call returns the Cloudflare API request it would send and never sends it. A result is about 100 tokens.

Server variants, described in full in [`docs/running.md`](docs/running.md#variants):

- `flat`: every tool in `tools/list`, skills over the Skills extension.
- `opt1`: Option 1's Groups server. Groups with authored instructions, no skills.
- `opt2`: Option 2. Groups, with a workflow group for each of the three skills that have API tools, which lists the skill. Descriptions as generated, two-level tree. 13 top-level groups on the subset and 139 on the full catalog.
- `opt2-rec`: Option 2 rebuilt to one level of groups with task-vocabulary descriptions, grouped skills left out of `skills/list`. 22 groups on the subset and 271 on the full catalog.
- `opt3`: Option 3. Option 2's bundles served under the skills method names.

Selection trial:

- The trial shows a model the listing a client sees before it opens anything and asks for one pick: a group, a skill, a tool or none.
- Flat names: every tool's name and first description line, with no groups.
- Skill index: the five skill names and descriptions from `skills/list`.
- First-call rule: strict scoring counts only the tools that do the job. The first-call rule also accepts a lookup the job would start with, such as `zones_list`. It was decided after the results.
- Open models: Qwen 3.5 9B, Qwen3 14B, GLM-5.3 Flash, DeepSeek V4.1 Flash, Qwen3.6 35B-A3B, Gemma 4 26B, with thinking off. Qwen3 14B has a 40k context and skipped the schema arm and the 3,036 flat names.
- Hosted models: Opus, Sonnet and Haiku 5.5, GPT-6 Astra, GPT-6.1 Sol, GPT-6.1 Terra, GPT-6 Luna, Gemini 4 Argon, Gemini 3.8 Flash, Kimi K3.1 Pro, each at its lowest reasoning setting.
- Classifiers: the OpenAI Decisions API on GPT-6 Luna, and TypeSafe's Jev. Each takes the groups as a list of choices and returns a pick with no generated text.

Claude Code conditions:

- The mod: [`mods/groups`](mods/groups), a Claude Code plugin that implements the Groups extension as three tools, `list_groups`, `open_group` and `read_skill`. See [`docs/running.md`](docs/running.md#the-claude-code-mod).
- Tool search: Claude Code's built-in deferral of tool schemas. A deferred tool is listed by name and its schema loads when the model searches for it. A resident tool has its schema in the prompt.
- Headless session: one `claude -p` run with the built-in file and shell tools disallowed.
- `groups`: the mod against `opt2`, scoped tools deferred behind the host's tool search.
- `groups-rec`: the mod against `opt2-rec`, scoped tools deferred.
- `groups-rec-resident`: the same with tool search off and scoped tools registered resident.
- `flat-toolsearch`: the flat server behind the host's tool search, with the mod supplying the skill index and `read_skill`.
- `flat-all-schemas`: the same with tool search off, so every schema is in the prompt.

Open-model runs, with the loop described in [`docs/running.md`](docs/running.md#the-open-model-agent-run):

- A: all 237 schemas in `tools` from the first request.
- B: starts with `list_groups`, `open_group` and `read_skill`, and appends a group's tools to `tools` when it opens.
- C: a fixed tool set of those three plus `call_tool`. `open_group` returns the schemas as tool-result text.
- D: all 237 tools in `tools` from the first request, each marked `defer_loading`. `open_group` answers with `tool_reference` blocks, which load the group's schemas. It ran on Baseten's own endpoint only.
- Scenario and phase: a scenario is six phases. A phase is one user turn that needs one or two tools from one group.
- Baseten and DeepInfra: the providers that serve the open models, reached through the Hugging Face router. Rows 14 and 15 also call Baseten's own endpoint, called Baseten direct.
- Cold: each session carries a unique id in its system prompt and in its first tool's description, so it reads nothing another session cached.
- Shared tool block: the id is left out of the tools, so sessions with the same tool list share its cached block. Row 13's cached arm A is a shared run made after a warm-up session.
- Padded results: about 2,000 tokens of filler added to every tool result.
- Strict and tolerant wrapper: the strict `call_tool` rejects a call whose tool name is nested inside `arguments`. The tolerant one accepts it and says what a rejected call was missing.
- Listing in the first tool: the group listing moved from the system prompt into the description of `list_groups`.
