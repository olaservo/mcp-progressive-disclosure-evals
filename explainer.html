Ola’s MCP groups research

The Groups extension says an MCP server should disclose its tools on demand. What does that help solve, and how much?

every table · the demo repository · the session traces · the working group's charter

What groups over MCP buy you, measured on one giant tools + skills catalog

An MCP server with a lot of tools and/or skills has a problem: by default, every tool's schema goes into the model's context on every turn, whether the task needs it or not. The MCP Progressive Disclosure working group (its repository, its Discord channel) has a draft Groups extension that answers this with two methods. groups/list returns a short list of named bundles, and groups/get returns one bundle's tools, prompts, resources and instructions when the agent decides it needs them. A companion document asks how Groups should sit next to Skills over MCP, which discloses instructions the same way.

I built both on a real catalog to see what the numbers look like. The server I used for this experiment is Cloudflare's own API MCP server, which includes 3,036 generated tools from 136 products, along with five of Cloudflare's published skills. One Worker serves it four ways: flat, and under each of the three positioning options the working group is weighing. Everything below was measured on the 2026-11-07 drafts of both documents.

Each finding is a paragraph and a chart or a small table. The full tables and the detail sit in collapsed sections underneath; open the ones you want.

How the server was built · the four variants and the three positioning options

One Cloudflare Worker on the TypeScript SDK 2.4.0 served the catalog four ways. A 238-tool subset from 10 products is deployed; the full 3,036 tools from 136 products run locally. Toolset groups mirror the generator's directory tree two levels deep, with templated descriptions ("Call the Cloudflare workers API directly. Use to read or change workers resources in an account."). Each workflow skill with API tools is also a group that scopes them and lists the SKILL.md. Tool calls were dry runs that return the request they would send.

Three things the numbers say

1. Groups solve a context-size problem, and it is definitely a problem at this scale. The flat tool list for 3,036 tools is 1.38 million tokens, more than any model can read. The groups list for the same catalog, using 139 top-level groups, is 5.5 thousand tokens. The bundle the agent then fetches for a task is the same size whether the catalog has 238 tools or 3,036. On a 238-tool subset the saving is still 157 thousand tokens down to about 700.

2. Groups did not measurably change what the hosted models picked. I gave sixteen models twenty tasks that describe a job without naming the product ("Serve 50 GB of user uploads to browsers on another origin, so cross-origin headers are needed") and asked where they would look first. Every hosted model scored similarly whether it saw 13 groups, 139 groups, 238 flat tool names or 3,036 of them. The draft already says this in its own evidence section: groups keep unread schemas out of context, but they do not beat using a flat list when it came to selection.

3. When testing through a real harness, the host's own tool search gets the same result. I wrote a Claude Code mod that implements the groups extension and ran the twenty tasks as 180 headless sessions, three models, three ways. Sonnet and Opus finished every task in every variant. Haiku finished 16, 18 and 19.

Groups cost a turn and 3 to 4 seconds per task. Opening a bundle is a round trip, and 5 of the 10 product groups on the subset hold only child groups, so those tasks open two. The prompt cache held when opening bundles: the request after a group open wrote a median 0.5k tokens to the cache on a prefix of about 21k. Claude Code's own tool search, with nothing from the extension, reached the same completion and the same token band using one less turn.

The charts and table in this section are the first round. In the second round, with a one-level tree and 300 sessions, groups read 1.54M to 1.75M input tokens per model and the host's tool search 1.51M to 1.60M. Groups took a median 5 turns on the product tasks against 3 or 4. The second round's table is in the results.

So what do groups solve?

Against the working group's own four criteria: groups deliver initial context size and total tokens, leave task completion unchanged for frontier models, and add a turn in exchange for each harness not needing to invent its own solution for reducing token bloat. On this catalog a host with tool search gets the token result. What groups add that tool search cannot is the bundle: a server-authored set of tools with the instructions and the skill that go with them, delivered together, scoped to the caller. The draft also argues groups give a client without tool search a path; the second round tested that, below. It also provides the same solution for skills served over MCP, and any other MCP primitive besides just tools. Harnesses are still working out how to handle large numbers of file-based skills (how harnesses bound their agent skills catalog), so a server-side bundle is one more reason to serve skills over MCP.

Two things the server author controls turned out to matter more than the mechanism itself. Group descriptions directly influenced the whole selection: my templated one-liners ("Call the Cloudflare queues API directly") cost the mid-size open models up to six of twenty tasks at 139 groups, which is what the draft's guidance warns about. And a server that offers both a workflow group and a plain toolset group for one product splits the models between them, so it should say in the descriptions which to open when.

Second round, 2026-11-09. A server rebuilt to the guidance in #19 (task-vocabulary descriptions and a shallow tree, here one level with a size cap of my choosing) closed the gap templated descriptions had opened. At 271 groups on the full catalog the open models scored 17 to 20 of 20, against 10 to 19 on 139 as-generated groups, and every hosted model scored 19 or 20. With tool search off in Claude Code, registering a group's tools resident saved the fetch turn and cost 2.2 to 2.4 times as much. The host keeps tool definitions in the cached prefix, so each open rewrites it, which the draft's prompt-caching section predicts for such clients. Appending tools after the prefix was not tested, and neither was any open model. Leaving grouped skills out of skills/list for a groups client left every model within one task of its score and removed the skill-only answers. The tables are in the results.

Held-out tasks, 2026-11-10. 20 tasks written by two models the demo does not test, from a product name alone, reproduced the second round. The recommended build scored 17 to 19 of 20 for the open models and 18 to 20 for the hosted models; the as-generated build cost five open models 3 to 14 tasks. On flat tool names the hosted models scored 18 to 20 once a lookup such as zones_list counted as a first call, a rule decided after the results. The tasks, accepted answers and both flat scores are in the results.

What the code showed about the positioning options · for the working group's two documents
  • Option 2 works as the positioning document's Example 3 describes. The turnstile-spin group scopes the six Turnstile tools and lists skill://turnstile-spin/SKILL.md; scripts/compare.ts confirms it with skills/get and reads it with digests verified.
  • Placement meets the SDK's default. The SDK's SkillCatalog lists every SKILL.md in resources/list, so a group that scopes one breaks the placement rule. A skill source without listResources fixes it. The draft's placement rule names only the three core listings, so skills/list is outside it by its text. What neither document says is whether a skill a group lists stays in skills/list. The skill-only picks above bear on it.
  • Scoped tools are callable without groups/get and stay out of that connection's tools/list. A client that does not declare the extension gets every tool.
  • Option 3 flattens the skill. When a SKILL.md folder becomes instructions plus scoped resources, the skill loses its entry (name, description, frontmatter), its digests, and the root that its relative references/*.md links resolve against. That is the concrete form of the mapping contract the document lists as Option 3's cost. Options 1 and 3 were compared on wire shape and tokens only.
  • Naming. The positioning document's prose says group/list in four places; its examples, the SEP and docs/decisions.md (since #23) say groups/list. A commenter asked about the same drift on #19 on 2026-11-09.

Caveats

This experiment only included one sample per task. The group names and descriptions are mine, not Cloudflare's. The full completion run using Claude Code used one model family on one host. It also tested against a dry-run server that returns the request a tool would send and never any data. The 'flat list' baseline is a mode Cloudflare itself ships only as an escape hatch; the server's default is Code Mode, which I did not compare, and I did not test per-caller scoping. The results have every table, every accepted answer and every limit, and the 180 sessions are also there to review.
