A second data point for "Early prototype evidence", from a larger catalog, with hosted models, and with a run through a real client. Full write-up: https://github.com/olaservo/mcp-progressive-disclosure-evals/blob/main/drafts/wg-findings-writeup.md. Code, raw answers and session files: https://github.com/olaservo/mcp-progressive-disclosure-evals.

**Setup.** A server on the TypeScript SDK 2.4.0 that implements this draft at `15b2a5c`. It serves the Cloudflare API MCP server's generated tools (cloudflare/mcp at `4938f2f3`): a 238-tool subset from 10 products, or the full 3,036 tools from 136 products. It also serves five skills from cloudflare/skills through the SDK's SEP-2640 extension. Toolset groups follow the generator's directory tree two levels deep, so the full catalog has 139 top-level groups. Their descriptions are templated one-liners. Each workflow skill that has API tools (Turnstile, Durable Objects, email) is also a group that scopes those tools and lists the skill's SKILL.md in `resources`, as Example 3 in #22 describes. Cloudflare ships this server behind Code Mode; the flat baseline here is its `codemode=false` direct-tool mode, and I did not compare groups with Code Mode itself. Token counts are tiktoken `o200k_base` over compact JSON, as in the earlier data point.

**Tokens, Turnstile task.** "Upfront" is everything the model reads before it commits to a task: `tools/list`, `groups/list` and the skill index. "Task load" is one `groups/get` plus the skill body.

| Catalog | Server | Upfront | Task load | Tools returned |
| :-- | :-- | --: | --: | --: |
| 238 tools | Flat `tools/list` with skills | 157,763 | 6,570 | 6 of 238 |
| 238 tools | Groups, instructions paraphrase the skill | 556 | 2,190 | 6 |
| 238 tools | Groups, group lists the skill | 743 | 8,768 | 6 |
| 3,036 tools | Flat `tools/list` with skills | 1,378,777 | 6,570 | 6 of 3,036 |
| 3,036 tools | Groups, 139 top-level groups, group lists the skill | 5,495 | 8,768 | 6 |

Task load does not grow with the catalog, since `groups/get` returns the same group either way. Once a group holds more than a handful of tools, the schemas are most of the load: the email group's 24 schemas cost about 7k tokens, the Turnstile skill body 6.5k. Scoped tools can be called on a connection that never issued `groups/get`, and they stay out of that connection's `tools/list`. A client that does not declare the extension gets the flat list. One snag: the SDK's skill catalog lists every SKILL.md in `resources/list`, so a group that lists a skill breaks the placement rule unless the server stops listing the skill there. I raised that on #22.

**Does the model pick the right group?** A selection trial, not task completion. Twenty tasks describe the job without naming the product ("Serve 50 GB of user uploads to browsers on another origin, so cross-origin headers are needed"). Some are confusable pairs (queues against Durable Objects, KV against D1 and R2), two are knowledge questions, two have no fit in the subset. One sample per task. The model sees the top-level tools, `groups/list` and `skills/list` as names and one-line descriptions, and answers with one pick: a group, a skill, a top-level tool, or none. The flat control shows every tool name and first line instead, with the same skill index. Six open models ran through the Hugging Face router with thinking off (Qwen 3.5 9B, Qwen3 14B, GLM-5.3 Flash, DeepSeek V4.1 Flash, Qwen3.6 35B-A3B, Gemma 4 26B). Ten hosted models ran at their lowest reasoning setting (Claude Opus, Sonnet and Haiku 5.5; GPT-6 Astra, 6.1 Sol, 6.1 Terra and 6 Luna; Gemini 4 Argon and 3.8 Flash; Kimi K3.1 Pro). With one sample per task, two cells within two of each other are the same result.

| What the model read | Tokens before the task | Six open models, correct of 20 | Ten hosted models, correct of 20 |
| :-- | --: | :-- | :-- |
| 13 groups and 5 skills (238-tool subset) | 633 | 16 to 19 | 19 to 20 |
| 139 groups and 5 skills (3,036-tool catalog) | 3,873 | 10 to 19 (14B 13, 35B-A3B 15, 9B 10) | 18 to 20 |
| 238 tool names and 5 skills, flat | 6,911 | 15 to 20 | 18 to 20 |
| 3,036 tool names and 5 skills, flat | 81,605 | 18 to 19 (9B 5; 14B skipped, 40k context) | 17 to 20 |

- Groups did not change what the hosted models picked. Each of them is within two tasks of itself across the four rows. What changed is how much they read first: 3,873 tokens instead of 81,605 at 3,036 tools, where the full schemas (1.38M tokens) cannot be read at all. This matches the finding the draft already cites: groups keep unread schemas out of context, they do not beat a list the model can read.
- Templated descriptions hurt the mid-size open models at 139 groups. Qwen3 14B went from 18 to 13, Qwen3.6 35B-A3B from 19 to 15, the 9B from 16 to 10. GLM, DeepSeek and Gemma held 17 to 19. The misses land on neighbours: `pipelines-api` for a dead-letter destination, `durable-objects` for relational tables, `iam-api` for rotating a token. The descriptions read "Call the Cloudflare pipelines API directly. Use to read or change pipelines resources in an account." That is what this draft's `description` guidance says not to write, so this row is the cost of ignoring it. Rewriting the descriptions for the confusable products and re-running is the next step.
- The skill index mattered more than groups against flat. My first run left `skills/list` out of the prompt. Adding it moved flat scores by up to 17 tasks (Haiku 5.5 from 7 and 1 of 20 to 18 and 17) and moved no groups-mode score by more than one. Eleven of the twenty tasks have a skill as a right answer, and the models take it. A client that implements groups but not SEP-2640 would see a different picture from one that implements both.
- Where a task accepts either the workflow (as a group or a skill) or the product's API group, the hosted models split about evenly at 13 groups and lean to the workflow at 139. A server that offers both for one product should say in the descriptions which to load when.
- Two classifier APIs got the group and skill names as choices. The OpenAI Decisions API on GPT-6 Luna picked right on 19 and 20 of 20 for about a cent in total. TypeSafe's Jev scored 20 and 16; its misses at 139 follow shared words, such as `pipelines-api` for "the orders pipeline".

**Task completion through a real client.** The same twenty tasks ran as headless Claude Code sessions, 180 in all. A mod speaks this extension to the server over HTTP the way the "Client behavior after `groups/get`" section sketches: client-side `list_groups` and `open_group`, and the group's scoped tools registered as deferred definitions when it opens. Two flat baselines: the flat server behind Claude Code's own tool search, and the flat server with all 238 schemas in the prompt up front. Claude Sonnet and Opus 5.5 completed 20 of 20 under all three conditions; Haiku 16, 18 and 19. Groups read 2.3M input tokens per model, against 16.5M to 18.4M with all schemas up front, and the same 2.0M to 2.4M band as the host's tool search. Groups cost a turn: median 5 against 3 or 4. Registering a group's tools as deferred added about 2.7k tokens on top of a 42k-token cached prefix, so the prompt-caching section's claim held on a shipped host.

Against the problem statement's criteria, then: groups deliver the context-size and token goals, leave completion unchanged for these models, and add a turn. On this catalog the host's tool search reaches the same token result with no protocol change. What groups add is the bundle, instructions and a skill delivered with the tools, and a path for clients that have no tool search. The sessions, reduced to their conversation rows, are in the repo.

**Limits.** One sample per task. The group names and descriptions are mine, not Cloudflare's. Accepted answers are my judgment and are listed in the write-up. Three completion tasks need data a dry-run server cannot return (a file, key names, namespace ids); every model took the right first step and said why it stopped, and I count that as done. The full-schema control (158k tokens at 238 tools, not run for Astra) landed within two of the names-only scores for every model that fits it. Every server lists a `demo_info` tool first, and two small models answered it on most flat tasks until a skill answer was available. The completion run is one model family on one host, and the tool-search arm is Claude Code's implementation.
